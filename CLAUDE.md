# Reponizer — internal architecture

Raycast extension for organizing a git-get style repository folder (`<root>/host/owner/repo`). This file is the single source of truth for how the project works internally; the README is user-facing only and must stay free of technical details.

## Tech stack

- **Raycast API** (`@raycast/api`) with React + TypeScript, bundled by `ray` (esbuild). `tsconfig` uses `moduleResolution: Bundler`.
- **git-url-parse** for remote URL parsing/normalization — do not hand-roll URL parsing anywhere else.
- Plain `execFile` for git (no simple-git); see `src/lib/git.ts`.
- No test framework; `scripts`: `build` (`ray build -e dist`), `dev`, `lint`, `fix-lint`, `typecheck`, `publish` (`ray publish`), `deploy` (`scripts/deploy.sh`: build to a local temp dir, then copy into `~/.config/raycast/extensions/reponizer` — the reliable way to deploy from the devcontainer, where that path is a virtiofs mount that direct writes sporadically corrupt; the script parks an undeletable extension dir as `*.trash-<ts>` and retries the copy once instead of failing).
- `raycast-env.d.ts` is generated by `ray build`/`ray develop` and committed.

## Data flow

1. `scan.findRepoDirs` walks the root (skipping hidden dirs and `node_modules`, stopping at repos) → repo dirs + offloaded dirs.
2. `inspect.inspectRepo` runs `git remote -v`, `status --porcelain=v2 --branch`, `stash list`, `log -1` in parallel (concurrency 8 across repos) → `Repo`. Failures produce an entry with `error` set — never a dropped repo. It then calls `fork.inspectFork`, which returns early unless the repo carries the configured upstream remote (`config.upstreamRemoteName`, pointing somewhere other than origin); only then does it pay for resolving an upstream ref (`rev-parse` over branch/HEAD/main/master) and `rev-list --left-right --count HEAD...<ref>`. Both steps are best effort — a never-fetched upstream still yields a `ForkInfo`, just without `ref`/`ahead`/`behind`. `headMovedAt` is the mtime of `.git/logs/HEAD` (no git call; absent when `.git` is a file), which "Last Activity" combines with `lastCommitAt`.
3. `inspect.buildIndex` assembles entries, sorts by relative path, marks duplicates (same normalized origin), and attaches sizes (`du -sk`, batched, reused from the previous index on fast refreshes).
4. `cache.ts` persists the `RepoIndex` as JSON in the Raycast `Cache`, keyed `index:v<CACHE_VERSION>:<root>`. **Bump `CACHE_VERSION` whenever `RepoIndex`/`RepoEntry` shapes change.**
5. `useRepoIndex` renders the cached index immediately, rescans in the background on mount (reusing sizes), and exposes `refresh` / `reconcile(fullPath)` / `refreshEntries(paths)` so actions update only what they touched. no-view commands write the same cache via `cache.ts`, so the next list open is fresh.

## Key invariants & conventions

- **Cache writes are serialized and merged against the freshest cached index** (`cache.patchFreshIndex`): every mutation (reconcile / refreshEntries / rebuild) patches what is currently in the cache, not the caller's snapshot — otherwise a slow bulk operation and a per-repo action would clobber each other. Route any new index mutation through it.
- **Untrusted strings never reach git argv unchecked**: `parseRemoteUrl` rejects leading-dash inputs, `readOffloadFile` validates origin/remotes from placeholder files, clone URLs are passed behind `--`, and remote names must match `^[A-Za-z0-9][\w.-]*$`. Fork and create targets follow the same rule: `targets.planTarget` (behind `planFork` and `planCreate`, whose `repoPath` also becomes the `gh repo create` argument) checks every path segment on its own via `config.isSafePathSegments`, because `coerceCloneUrl` only rejects a leading `-` on the whole string and `owner/-x` would otherwise reach git argv as a flag. Preference values that end up in argv (upstream remote name, fork namespaces) are validated with `config.HOST_TOKEN` — same regex, same reason. Keep these guards when adding git calls.
- **Remote comparison is protocol-agnostic and alias-aware**: `normalizeRemoteUrl` maps the host into canonical alias space (`config.getHostRules`, preference `hostAliases`, `alias=realhost` pairs), lowercases, and strips `.git`; only canonical host+path identity matters. Expected origin for `host/owner/repo` is derived in `remotes.expectedOriginFor`; the first segment may be a dotted hostname or a configured alias (anything else → `unstructured`). Hosts listed in the `hostOnlyHosts` preference (alias or real form) are compared by host identity only — `expectedOriginFor` returns `undefined` for them (no Fix Origin offered) and `checkRemotes` reports `ok`/`mismatch` from the origin host alone (Overleaf-style opaque repo paths).
- **`RemoteCheck.state`** drives all "deviation" UI: `ok | mismatch | no-origin | no-remotes | unstructured | unknown`. Fixes offered: set origin to expected (preserving the current origin's protocol), or relocate the folder to match origin.
- **Offload safety**: `offload.findUnsyncedState` fetches origin first, then blocks on uncommitted/untracked changes, stashes, and any branch that is ahead, upstream-less, or tracking a gone upstream. The working copy is renamed aside, the placeholder (`reponizer-offloaded.json`, schema `reponizer/offloaded`, includes origin + all remotes + branch + size) is written, then the copy is trashed; failures roll back. Restore refuses non-empty folders and re-creates the placeholder if the clone fails.
- **Pull is always `--ff-only`** and skips dirty/detached/conflicted/upstream-less repos (`ops.pullRepo`). Never introduce merging pulls.
- **"Publish Branch" is the one-branch push**: `ops.publishBranch` runs `push --set-upstream origin HEAD` and is offered only while `ops.hasUnpublishedBranch` holds (origin present, branch attached, has commits, no upstream). Unlike the fork's "Push to Origin" it never carries other branches or tags.
- **"Sync from Upstream" is fast-forward only too** (`fork.syncForkRepo`: fetch the upstream remote, then `merge --ff-only <upstream-ref>`). It skips dirty/detached/conflicted repos, repos without a matching upstream branch, `behind === 0`, and anything with local commits ahead of the upstream ref. Never introduce a merging or rebasing variant.
- **New repositories reach their host through one path, `hosting.provisionRemote`** (create and fork alike): the local side is complete first, then `creationMethodFor` (alias-aware) picks the route. How hosts create repositories differs per platform, so nothing is assumed and every host — GitHub included — is handled the same by default. **github-cli** is an opt-in: the "GitHub CLI" checkbox the create and fork forms show for github.com targets only (`isGitHubHost`; the flag reaches `planCreate`/`planFork` as `useGitHubCli` and counts nowhere else). It runs gh, and only after gh succeeded is anything pushed (`published`, or `push-failed` — the repository exists, a plain push retries); **push** (hosts in the `pushToCreateHosts` preference) pushes right away and relies on the host creating the repository; **manual** (everything else) pushes nothing. A failed gh (missing `ENOENT`, logged out exit code 4 per `gh help exit-codes`, name taken, …) or a refused push-to-create is `needs-remote` with the reason; so is manual, without one. `needs-remote` means the user creates the repository on the host (`remotes.hostWebUrl`, deliberately just `https://<host>` — creation pages differ per platform) and pushes afterwards: "Publish Branch" for created repos, "Push to Origin" for forks. `provisionRemote` never throws and nothing after the local setup is rolled back. Before any local change, `hosting.remoteState` (`git ls-remote`) looks at the target URL on **every** host: a repository with commits stops the create or fork (`existingRepoError`) — pushing would add a branch next to what is there, and "create it by hand" would be impossible; an existing empty repository (created by hand earlier, say) takes the **push** route whatever the host, since it only needs the push; a failed lookup counts as missing, which is why it runs from `os.tmpdir()` rather than the repos root — before the first repository the root may not exist, and that failure would skip the check. `remoteOutcome.showRemoteOutcome` turns the outcome into the toast.
- **Repository creation** (`create.executeCreate`) sets up the local side first (`git init`, origin, `commit --allow-empty` — a push needs a commit, and the folder stays empty); a failure there removes what it created (the whole folder when it was new, only `.git` in a pre-existing empty one) and the form stays open. Before anything runs, the form refuses what `targets.placementProblem` reports from the index: a taken path, a path inside another repo or placeholder, or one deeper than `maxDepth` segments — the scan would never find the last two, so they would vanish on the next rescan (the fork form and the clone form's fork variant use the same check). A ref (not state) blocks a second submit while one is running, since its rollback could remove the first one's folder; the fork forms have the same guard. The three forms share their wording and fields (searchable host, GitHub-specific namespace hint and error) — fork's through `ForkView.forkFormFields`.
- **Forking** (`fork.executeFork`, and `forkFreshCopy` after a clone in the clone form's fork variant): `claimForkTarget` runs everything that may refuse the fork *before* the local copy changes — "Current Branch" without a checked-out branch, the `remoteState` check, and the real GitHub fork below — and `setUpFork` needs its `ForkClaim`, so the order cannot be skipped. The move variant checks that the target folder is free even before that (`ops.assertRelocationTarget`), since a GitHub fork must not exist for a fork that then fails locally; copies made for the fork alone (keep-original clone, clone form) are removed again when the claim refuses. Then branches are materialized (scope "all"), the remotes rewired (origin → fork target, previous origin kept as the upstream remote), and `provisionRemote` runs. With the GitHub CLI opted into, a source that is itself on GitHub, under another owner (`fork.gitHubForkSource` — GitHub never forks into the owning account, that case is a `gh repo create` copy), becomes a **real fork**; it needs a free name, so an existing empty repository at the target stops it too (`POST repos/{source}/forks` via `gh api`, not `gh repo fork`, whose `--fork-name` renames an already existing fork). GitHub keeps one fork of a repository per account and the endpoint hands back the existing one instead of failing, so `forkGitHubRepo` tells them apart by `created_at` (older than a minute = existed, gh's own heuristic) and *throws* for an existing fork or one that landed under another name — never reused, never renamed. A local failure *after* a real fork was made is rethrown by `withGitHubFork` saying that the fork exists, since running the fork again would be refused. Other gh failures (missing, logged out) only mean the user forks by hand. A real fork gets every branch and tag from GitHub, so it pushes nothing (`planFork` forces scope "none") — pushing stale local branches onto it would only be rejected. Other GitHub targets use `gh repo create` with a visibility. Manual hosts always prepare scope "all" for the later "Push to Origin" (which pushes all local branches and tags); scope "none" on a push-to-create host becomes manual, since pushing nothing creates nothing. "Push to Origin" only exists for forks (it needs the upstream remote): a fork of a repository without an origin gets no upstream, so its toasts point at "Publish Branch" instead.
- **Forking into a copy materializes tracking branches first**: in the `keepOriginal` variant the clone's `refs/remotes/origin/*` (the checkout's own branches) are turned into local branches *before* `git remote remove origin`, because removing the remote deletes the tracking refs and `push --all` would otherwise carry only the checked-out branch. A clone of a local folder does not carry that folder's remote-tracking branches, so `adoptTrackingBranches` also creates the checkout's `origin/*` branches in the copy (their commits come along with the object store); the checkout's own branches win.
- **Destructive actions** (trash, offload, delete remote, fix origin, relocate) always go through `confirmAlert`.
- **No silent error swallowing**: git failures surface as `GitError` (its message carries the last `fatal:`/`error:` stderr line — clone prints progress to stderr first), toasts include a "Copy Error/Failures" action (`util.errorDetails` copies the full stderr), broken repos render with a red icon + tooltip.
- **Raycast env quirk**: preferences are the runtime configuration surface (Raycast has no env vars); `git.ts` repairs `PATH` and `SSH_AUTH_SOCK` because Raycast doesn't run a login shell. Raycast's `PATH` lacks `/bin`, where macOS keeps `sh`: git itself uses an absolute `/bin/sh`, but git-lfs looks `sh` up via `PATH` for its local-path transfer and reports the miss as `failed to find custom transfer command "git-lfs"`, so keep `/bin` in the repaired `PATH`. `gh` (Homebrew: `/opt/homebrew/bin` or `/usr/local/bin`) is only found through the same repaired `PATH`, so it runs via `git.run`.
- Export schema is `reponizer/repos` v1: `{ path, origin?, remotes?, offloaded? }` per entry. Import never deletes; it clones missing repos (concurrency 2) or writes offload placeholders. Local-only repos are only reported.
- All user-visible paths are POSIX-relative to the root (`github.com/owner/repo`); `group` (dirname) is the list section title.

## Extension points

- **New list filter**: add a value to `Filter` + a branch in `matchesFilter` (`lib/filters.ts`) and an item in the dropdown (`search-repos.tsx`).
- **New sort order**: add a value to `SortOrder` + `SORT_ORDERS` and a branch in `sortEntries` (`lib/sorting.ts`); the "Sort Order" section of the search-bar dropdown and the "Sort by" submenu (`⌥⌘S`) list it automatically; the order is persisted in the `Cache` under `sort-order`. Every order but `path` renders one flat section with the group as item subtitle.
- **New per-repo action**: add to the matching section component in `RepoActions.tsx`; use `withToast` + `ctl.reconcile(fullPath)` after mutating.
- **New bulk operation**: implement an `(repo) => Promise<OpResult>` in `ops.ts` and reuse `runBulkCommand` / `runOnRepos`. Inside the action panel the helper is the module-level `bulkAction(ctl, title, op, select?)` in `RepoActions.tsx`; the optional selector narrows the run to a subset of the healthy repos ("Sync All Forks from Upstream" passes `(repo) => !!repo.fork`).
- **New entry state on disk**: extend `scan.ts` detection, add a `kind` to `RepoEntry`, bump `CACHE_VERSION`.
- **New creation method** (e.g. a host API with a token): add a `CreationMethod`, route hosts to it in `hosting.creationMethodFor` (an opt-in like the GitHub CLI's, so the default stays the same for every host), and handle it in `provisionRemote` the way the GitHub CLI is handled: on success, push and report a failed push as `push-failed`; on failure, return `needs-remote` with the reason. Create and fork both pick it up.
- **New command**: add the manifest entry in `package.json` (name must match the `src/<name>.tsx?` file) plus the source file.

## Gotchas

- `Cache` is shared across all commands of the extension — that is what makes no-view commands able to update the list's data.
- `git-url-parse`'s `full_name` includes GitLab subgroups (`group/sub/repo`); code must not assume exactly `owner/name`.
- Offloaded placeholders make `cloneRepo` fail with a pointer to "Restore Local Copy" instead of cloning over the folder.
- `confirmAlert` centres its message and has no alignment option, so dialogs keep lines short instead of labelling them: `util.describeTransition` puts a from/to pair on separate lines with the arrow between. Raycast also truncates the message after a few lines ("…"), so the explanatory sentence goes into the alert title, never as a lead line above the pair. Multi-fact strings joined with `·` or `→` wrap mid-path and are unreadable there; labelled key/value layout belongs in `Form.Description` rows (`ForkView`, clone form), which Raycast left-aligns.
- Raycast's native dropdown filtering (`filtering`) breaks when the items change while the user searches, e.g. to offer the typed text as an item of its own. Searchable host/namespace dropdowns therefore pass `filtering={false}` and get pre-filtered items from `targets.targetOptions`: matches, then the typed value, then the current value — a controlled dropdown must always contain its value, and last it never takes the highlight (and the Enter key) from a match. Picking a value clears the query (`useRepoTarget`), since a leftover query would still filter the next time the dropdown opens.
- Raycast `Form` children must be direct `Form.*` elements — a wrapper component rendering several fields is not accepted. Shared form logic therefore ships as a hook: `hooks/useRepoTarget.ts` holds the host/namespace state plus the option lists, and each form (`ForkView`, the clone destination form, `CreateRepoForm`) renders its own `Form.Dropdown`s from it.
- The search bar takes a single accessory, so filter and sort order share one `List.Dropdown`. It is controlled by the filter (persisted in the `Cache` under `filter`, not `storeValue`): sort items carry a `sort:` value prefix, and picking one changes only the order, so the dropdown keeps showing the filter. A remembered host/owner filter that no longer exists falls back to "all", since a controlled dropdown must contain its value.
- A background launch (`environment.launchType === LaunchType.Background`, from a manifest `interval`) must not show toasts, HUDs, or alerts — they would fire on a timer, and Tinycast suppresses them. Report through `updateCommandMetadata` (the command's subtitle) and throw to have the launcher mark the command as failed. Interval commands stay `disabledByDefault`, so nothing runs on a schedule unless the user opts in.
- The menu bar command runs on an `interval` and must stay cheap: it renders from the cache and only rescans on explicit "Rescan Now".
- `ray lint` enforces Prettier (printWidth 120) and Raycast eslint rules; run `npm run fix-lint` before committing.

### Raycast Store constraints

The extension targets the Raycast Store, so these are hard requirements, not preferences:

- `package.json` `author` must be the Raycast account username; `license` must stay `MIT`; keep `@raycast/api` on the latest major.
- Every user-visible title is Title Case: extension title, command titles (`<verb> <noun>`), action panel items, dropdown items, section titles.
- Never set `navigationTitle` on a root command, and never derive any navigation title from state — Raycast owns the root title, and nested screens get short static ones.
- Every `List`/`Grid` needs a `searchBarPlaceholder` and an `EmptyView`; every text field and text area needs a `placeholder`.
- US English only, no localization, no external analytics or telemetry of any kind.
- `assets/` is for runtime images only (`icon.png`, 512×512, legible on light and dark); keep it free of unused files. README media goes in a top-level `media/` folder.
- `metadata/` holds 2000×1250 PNG store screenshots (three to six), captured with Raycast's Window Capture in development mode with “Save to Metadata” ticked. It is macOS-only work and cannot be produced from the devcontainer.
- The README's screenshots are copies of the store screenshots in `media/` under descriptive names (git stores identical files once); re-copy them whenever `metadata/` changes.
- The changelog entry for an unreleased change uses the `{PR_MERGE_DATE}` placeholder instead of a literal date.
